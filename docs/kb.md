# 회계감사기준 지식베이스

기준서 문단을 담은 SQLite 지식베이스와 그 위의 지식그래프 · 검색 · RAG 채점. 문제 점검 · AI 채점의 근거 · 게임의 근거 표시 · 탐색기가 같은 데이터를 쓴다.

원문은 저작권이 있어 저장소에 없다. 저장소에는 코드 · 측정 방법 · 문단 번호만 둔다. 만들어진 데이터는 `자료/kb/`(.gitignore)에 있다.

## 원문 판본

「회계감사기준 전문(全文) (2026년 개정)」. 2026년 7월 개정, 금융위원회 승인 2026. 7. 31., 한국공인회계사회 게시 2026. 8. 6. 2026. 11. 3. 게시판 대조 때 이것이 최신 전문이고, 그 뒤 글은 720 적용 FAQ(2026. 8. 26.)뿐이다.

전문에는 아직 시행되지 않은 개정이 함께 실려 있다.

| 기준서 | 시행 시기 | 다루는 법 |
|---|---|---|
| 220 | 상장사 감사인 2027. 12. 31. 이후 개시, 그 밖 2029. 12. 31. 이후 개시 | 전문에는 개정판만 있다. 시행 중인 구판 문단은 2025 전문에 있고 이 데이터에는 없다 |
| 720 | 자산 5천억 이상 상장 2026. 1. 1. 이후 개시, 그 밖 2027. 1. 1. 이후 개시 | 게임은 개정판 기준 |

- 용어: 220 개정판은 업무품질검토, 2026 기출 · GS와 전문의 다른 기준서는 업무품질관리검토. 게임 화면은 업무품질관리검토로 쓰고 채점은 둘 다 받는다(`data/lexicon.js`).
- 250-10 시행일의 `202X년`은 추출 오류가 아니라 Word · PDF 공통 원문 표기다.
- 600은 2025 · 2026 개정 대상이 아니다. 유의적 부문 · 부문중요성 구조가 현행이다. ISA 600 (Revised)의 구조는 아직 들어오지 않았다.

## 구조

```
회계감사기준 전문 .docx
   │  tools/kb_build.py     Word 자동 번호를 되살려 문단으로 쪼갠다
   ▼
자료/kb/ksa.jsonl           문단 { id: '505-8', std, no, kind, title, heading, text, items[] } — 비교해 보기 쉬운 중간 산출물
   │  tools/kb_db.js        스키마 · 문단 · 전문 색인 (이전 DB 의 벡터 · 채점 기록은 옮겨 담는다)
   ▼
자료/kb/ksa.db              SQLite 하나 — 문단 · 전문 색인 · 지식그래프 · 벡터 · 채점 기록
   │  tools/kb_graph.js     지식그래프 (원문 구조 · 개념 · 기출 · 해설 인용 · 게임 논점)
   │  tools/kb-embed.mjs    문단 벡터 (로컬 모델, 이 PC 에서만 계산)
   │  tools/kb-link.mjs     게임 논점 → 근거 문단 (검색 후보 → Claude 검증) → data/kb_links.js
   ▼
tools/kb-retrieve.mjs       근거 찾기 — BM25 · 벡터 · 혼합 · 그래프 확장, 측정으로 고른 기본 경로
   ├─ tools/kb-ground.mjs   채점 요청에 [근거 문단] 을 붙인다 (RAG) · 채점 기록      ← tools/serve.mjs /api/grade
   ├─ tools/kb-api.mjs      그래프 탐색기 읽기 API                                  ← tools/serve.mjs /api/kb/* · kb.html
   └─ tools/kb-eval.mjs     검색 방식별 측정
```

한 번에 다시 만들기: `node tools/kb-rebuild.mjs` (원문부터면 `--docx "<전문 .docx>"`). 벡터는 글이 같으면 다시 계산하지 않는다. 채점 서버가 DB 를 열고 있으면 파일을 바꾸지 않고 내용을 덮어쓴다(SQLite backup) — 새 내용은 서버를 다시 켜면 읽는다.

## DB

SQLite 파일 하나다. 게임에는 서버가 없고, Node(`node:sqlite`) · Python(`sqlite3`) 양쪽에서 그대로 열린다. 스키마 판은 `PRAGMA user_version`(지금 2). 채점 서버 · 탐색기가 읽는 동안 벡터 · 그래프를 쓸 수 있게 WAL 로 둔다.

| 표 | 내용 |
|---|---|
| `meta` | 스키마 판 · 만든 때 · 원본 JSONL 의 SHA-256 · 벡터 · 그래프 · 연결을 만든 때 |
| `standard` | 기준서 번호 · 제목 · 문단 수 |
| `paragraph` | 문단 id(`505-A12`) · 기준서 · 번호 · 종류(요구사항 · 적용지침 · 보론) · 제목 · 본문 · 항목(JSON) · 전문 안의 순서 |
| `paragraph_fts` | 전문 색인. FTS5 trigram — 조사가 붙은 한국어도 문구 그대로 찾는다 (`kb.js grep`) |
| `node` · `edge` | 지식그래프. 엣지는 (출발, 관계, 도착, 출처)가 한 줄이고 가중치 · 신뢰도를 갖는다. 외래키로 노드에 묶인다 |
| `vector` | 모델마다 색인 단위 하나에 벡터 하나(Float32). 단위 글의 sha 가 같으면 다시 계산하지 않는다 |
| `grading_log` | RAG 채점 기록 — 붙인 문단 · 논점별 인용 · 판정 · 걸린 시간. 답안 글은 남기지 않는다 |

`kb.js` 의 `eval` · `check` · `find` 는 DB 로 옮긴 뒤에도 JSONL 로 읽을 때와 출력이 한 줄도 다르지 않다. `PRAGMA integrity_check` ok · 외래키 위반 0.

## 번호 되살리기

기준서의 문단 번호는 글자가 아니라 Word 자동 번호라서 텍스트로 뽑으면 사라진다. 번호가 하나 밀리면 인용이 전부 틀리므로, 이 층의 품질은 번호에서 결정된다. 원본에서 확인한 규칙은 다음과 같다.

| 원본의 모양 | 처리 |
|---|---|
| `문단` · `문단A` 스타일, 번호 형식 `%1.` · `A%1.` | 본문 번호로 센다 |
| 같은 스타일에 번호 형식만 `(%2)` · `(%3)` · `%1)` · `%4.` | 앞 문단의 목록 항목 (330 · 402 · 600 · 705) |
| 같은 스타일에 `numId` 0 | 번호 없는 이어지는 글 |
| 2열 표 안의 문단 | 문서 순서대로 읽는다 (315 문단 21~26) |
| `보론 제목` 뒤 | `보론n-` 번호로 따로 센다 |

`node tools/kb.js check` 는 요구사항과 적용지침의 상호 인용이 서로 맞는지 본다. 한 요구사항이 여러 절을 가리키는 경우가 있어 100%는 나오지 않지만, 번호가 밀리면 그 기준서 전체가 어긋나므로 바로 드러난다.

## 검색

- BM25 — 한국어는 조사가 붙어 낱말 경계가 흔들리므로 글자 두 자씩 색인한다. 500자가 넘고 항목이 둘 이상인 문단은 항목별로도 색인한다. 채점 사전(`data/lexicon.js`)으로 질의를 넓힌다
- 벡터 — `Xenova/multilingual-e5-small`(8비트 · 384차원). 같은 측정에 `Xenova/multilingual-e5-base`(8비트 · 768차원)도 넣어 크기를 견줬다. 색인 단위 4,669개. 실행기(`@huggingface/transformers` 4.3.1)와 모델은 저장소 밖 `%LOCALAPPDATA%/audit-sim-kb` 에 둔다. 원문은 이 PC 밖으로 나가지 않는다. 이 PC(i5-5200U · 2코어)에서 e5-small 은 단위당 0.18초 · 질의 15ms, e5-base 는 단위당 약 0.7초
- 혼합 — BM25 와 벡터의 순위를 RRF 로 합친다
- 그래프 확장 — 위쪽 문단의 적용지침 · 요구사항 · 참조 문단에 점수를 나눠 준다
- 소규모기업 기준(1200)은 본 기준서와 내용이 겹쳐 기본 결과에서 뺀다

읽는 법

- 문단을 정확히 찾는 데는 기준서를 알 때도 모를 때도 BM25 가 가장 정확하다. 기본 경로가 BM25 인 까닭
- 혼합은 기준서 고르기에서 BM25 와 비슷하고(140건 중 1건 차이), 게임 논점의 기준서 고르기에서만 조금 낫다(1위 61.9% · 57.8%)
- 벡터만으로는 어느 층에서도 BM25 에 못 미친다. 큰 모델(e5-base)이 작은 모델보다 낫지도 않았다
- 문단 단위 질의는 스캔 해설의 OCR 글이라 잡음이 많고, 건수가 적어 1건이 1.3%p 다

## RAG 채점

```
브라우저 (js/aigrade.js)                         채점 서버 (tools/serve.mjs)                       Claude Code
  채점표 · 답안 → 요청 글                           ground { q: 물음 + 논점 + 뜻, stds: 장면 기준서 }
  + ground { q, stds }          ──POST /api/grade──▶ kb-ground: 근거 문단 5개 (기본 경로)
                                                    요청 글 끝에 [근거 문단] 을 붙인다    ──────────▶ 논점마다 full · half · none
                                                    cite 를 붙인 번호로만 거른다           ◀────────── + cite (근거 문단 번호 0~2)
  채점표: 논점마다 「근거 505-8」                ◀── { out, ground }  · grading_log 에 기록
```

- 질의는 답안이 아니라 물음 · 논점 · 뜻으로 만든다. 같은 문항이면 늘 같은 근거가 붙어 채점이 흔들리지 않는다(문항마다 캐시)
- 근거 문단은 「판정 참고」다. 채점 기준은 여전히 채점표이고, 채점표에 없는 논점을 더하지 않는다 (지침 5)
- 서버가 처음 뜰 때 지식베이스를 미리 읽는다(0.6초). 근거 검색은 문항당 평균 8ms(같은 문항은 캐시)
- 장면의 근거가 윤리기준 · 법령뿐인 문항에는 붙이지 않는다. 장면 기준서는 「KSA 505」 꼴만 읽는다
- API 키 길(배포판)에는 지식베이스가 없어 근거 문단이 붙지 않는다

같은 답안을 근거 없이 · 근거를 붙여 채점해 견준다 — `node tools/aigrade-calib.mjs --n 12 --model claude-sonnet-5-5 [--rag]`

| 항목 (기준 90%) | 근거 없이 | 근거 붙임 |
|---|---:|---:|
| A 모범답안 — 전부 인정 | 97% | 97% |
| A 감점 없음 | 100% | 100% |
| B 다른 문항의 답 — 전부 불인정 | 93% | 93% |
| C 배점 큰 논점을 뺀 답 — 그 논점 감지 | 100% | 100% |
| A = A' 같은 답 두 번 — 같은 판정 | 92% | 92% |
| D 같은 뜻 다른 말 — 인정 | 6/6 | 6/6 |
| 오류 | 0 | 0 |

근거 붙임 — 요청 54번 · 평균 5.0개 · 근거를 인용한 논점 44% · 붙이지 않은 번호 인용 0건 · 근거 검색은 장면 기준서 안 평균 8ms · 기준서를 모를 때 평균 5ms (서버가 뜰 때 0.6초 준비)

- 근거를 붙여도 채점이 흔들리지 않았다. 근거 문단이 판정 기준을 바꾸지 않게 한 지침 5 가 지켜졌다
- 일치율을 올리지는 않았다 — 채점표 기준으로 이미 90% 이상이다. 얻은 것은 판정마다 기준서 근거를 보이는 것
- 인용은 논점의 절반 아래다. 장면 속 사실 · 회계처리 논점에는 근거를 달지 않는다
- 이 측정 전에 장면의 기준서가 채점 요청에 안 넘어가던 문제를 고쳤다. 위 숫자는 고친 뒤의 것

## 게임 논점 ↔ 근거 문단

`node tools/kb-link.mjs --verify`

1. 후보 — 장면 기준서 안 BM25(물음 + 논점) 3개와 논점만으로 전체 혼합 검색 3개를 합친다
2. 검증 — Claude(Haiku 5.5)가 후보 문단을 읽고 이 논점의 직접 근거만 0~2개 고른다. 감사기준서 밖 내용이거나 장면 속 사실을 적은 논점이면 고르지 않는다
3. 공개 — 검증에서 고른 것만 `data/kb_links.js` 에. 문단 번호와 논점 이름뿐이다. 게임은 놓친 논점 옆에 「근거 KSA 505-8」 을 보인다(AI 채점이 아니어도)

| 단계 | 수 |
|---|---:|
| 게임 논점 | 719 |
| 지식베이스 밖 — 윤리기준 · 법령만 다루는 장면의 논점 | 37 (후보를 고르지 않음) |
| 후보 — 논점마다 4~6개 | 논점 682 · 후보 엣지 3,504 |
| 검증 — Haiku 5.5, 8개씩 묶어 호출 | 682 (실패 0) |
| 근거를 고른 논점 | 574 (84%) · 문단 937 · 기준서 34곳 |
| 고르지 않은 논점 | 108 — K-IFRS 회계처리 · 장면 속 사실 · 후보에 직접 근거 없음 |

표본 40개를 원문과 대조했다 (개발 중 검토. 사람 검수는 따로 한다)

| 방식 | 맞은 논점 |
|---|---:|
| 검색 1위 하나 | 16 / 40 (40%) |
| 두 검색이 같은 문단을 고를 때만 | 60% (논점의 49% 만 공개) |
| 후보 + 검증 (지금) | 32 / 40 (80%) |

검증이 고른 문단 48개 — 직접 근거 33 (69%) · 관련은 있으나 직접은 아님 12 (25%) · 틀림 3 (6%). 고르지 않은 10개 중 9개는 고르지 않는 게 맞았고, 1개는 근거 문단이 후보에 없었다(검색이 놓침).

## 그래프 탐색기

`node tools/serve.mjs` 후 `http://localhost:8765/kb.html`

- 탐색 — 문단 찾기(결과마다 BM25 · 벡터 · 그래프 가운데 어디서 걸렸는지), 문단 원문, 이웃 그래프(관계마다 가까운 몇 개), 관계별 목록
- 커버리지 — 기준서마다 기출 · GS 문항과 해설 인용(출제 무게)과 검증된 게임 논점 · 장면 · 카드를 견준다. 출제 무게가 위쪽 절반인데 게임 논점이 그 절반에 못 미치면 빨간 줄
- 채점표의 근거 번호를 누르면 그 문단이 열린다. 이 PC 서버에서만 — 원문은 밖으로 나가지 않는다

## 공개 범위

| 저장소 · 배포본 | 이 PC 에만 (`자료/` · `%LOCALAPPDATA%`) |
|---|---|
| 코드 · 스키마 · 측정 방법 · 이 문서 | 기준서 원문(`ksa.jsonl` · `ksa.db`) |

| `kb.html` — 데이터는 로컬 API 로만 | 벡터 · 채점 기록 · 검증 결과 · 모델 · 실행기 |

## 한계

- 감사기준서만 들어 있다. 윤리기준 · 외감법 · 공인회계사법 · K-IFRS 는 원문이 없어 그런 논점은 근거를 고르지 않는다
- 벡터 모델은 이 PC 사양에 맞춘 다국어 모델이다. 문단 구분은 BM25 보다 못했고, 더 큰 모델도 나아지지 않았다. 감사기준 문장으로 미세조정한 모델은 아직 없다
- 일상어로 물으면 놓칠 수 있다. 「회신이 오지 않을 때」 로 찾으면 기준서의 「미회신」 문단(505-12)이 5위 안에 없다. 「재고자산 실사 입회를 할 수 없는 경우」 는 BM25 로 501-A13 만 5위, 혼합으로는 501-A12 · A13 이 2 · 3위 — 탐색기에서 방식을 바꿔 볼 수 있다. 채점 질의는 채점표의 기준서 용어로 만들어 영향이 작다
- 논점 ↔ 근거 연결은 Claude 검증을 거쳤지만 사람이 전부 본 것은 아니다. 표본 정확도로 보고한다
- 그래프 확장은 순위 개선이 측정되지 않아 기본 검색에서 뺐다
